## 分工

- **仓库维护者**在规划账号的对话中提出需求和调整方向，决定是否合并。
- **规划账号**把定稿需求、实施建议和验收标准写入任务单。收到交付后，优先核对 PR 差异和已有证据，只对证据缺口做针对性检查，并向仓库维护者报告结论。
- **执行账号**读取任务单，以指定的 `main` 提交为基准创建任务分支，完成修改、测试和取证，然后向 `main` 开草稿 PR。任务单所在的 `handoff` 分支用于读取交接材料，产品改动提交到任务分支。

## 执行账号如何交付

1. 在 PR 标题注明任务编号，在正文贴上任务单链接，注明实施所依据的任务单版本。
2. 写明改动摘要、被测试的 commit SHA，以及每项验收标准对应的证据。附实际执行的命令和结果，标明失败、未运行项及原因。任务单要求截图时，附截图或可访问链接，并注明页面、窗口尺寸和交互状态。
3. 遇到需要决定的范围变化或无法完成的验收项，在 PR 或关联的 GitHub Issue 中说明问题和可选方案。返工时在同一 PR 更新 commit 和受影响的验证结果。
4. 将结果留在 GitHub 的 PR 中。仓库维护者决定是否合并。MeshLab 合并到 `main` 后会触发 Pages 工作流。

任务队列是公开的。任务单和交付证据只放可以公开的内容。新任务采用[任务模板](TASK-TEMPLATE.md)。
